安卓内存自动化脱壳与提取工具 (UltimateTool.py) 使用说明
这份 UltimateTool.py 是经历了无数个坑（计算偏移错误、内存碎片污染、壳伪造 DEX 大小、SO 头损坏）之后，最终沉淀下来的安卓内存脱壳与提取全流程自动化脚本。
它专为对抗现代加固（如梆梆企业版）设计，完全摒弃了常规提取中“相信头部声明”的脆弱逻辑。

📂 一、 目录结构与作用
脚本运行后，会在同级目录下自动创建三个核心文件夹：
1. memory_dumps/：存放从手机内存直接 dd 出来的原始二进制内存块。
2. extracted_dex/：存放经过暴力截取和头部修复的 .dex 文件，可直接拖入 Jadx。
3. extracted_so/：存放从内存中抠出来的 .so 文件，可直接拖入 IDA。

🧠 二、 核心处理逻辑（为什么这么写？）
1. dump_memory()：自动过滤与精准切割
• 痛点：手机内存映射（maps）巨大，里面全是垃圾数据；Windows CMD 无法计算大十六进制数，导致 dd 失败。
• 处理逻辑：
◦ 脚本自动读取 maps，只抓取 rw-p 或 rwxp 的内存段，自动过滤掉堆栈、位图等无用碎片，只保留大于 2MB 的有效数据块。
◦ Python 在后台自动把十六进制地址转换成十进制，生成绝对正确的 skip 和 count 参数，彻底告别手算错误。
◦ 每次拉取完文件，自动删除手机上的临时文件防止撑爆存储。
2. extract_dex()：对抗“函数抽取”的暴力修复
• 痛点：壳在内存中生成的 DEX 头部声明大小往往是假的，真实方法体跟在后方的内存里。老实按大小截取会丢掉核心代码。
• 处理逻辑：
◦ 暴力切尾：找到 dex\n035 魔数后，完全无视头部声明的大小，直接从魔数位置一直截取到内存块末尾。
◦ 强制修复：把切出来的数据强行修正 file_size 并重算 SHA-1 和 Adler-32 校验和。Jadx 依靠内部 map_list 会自动忽略尾部多余垃圾，成功反编译出完整类。
3. extract_so()：对抗“节头抹除”的兜底方案
• 痛点：壳会把 .so 文件的节头表（Section Header）抹掉或篡改，导致常规脚本解析出 0 字节。
• 处理逻辑：
◦ 放弃解析，强行截断：找到 \x7fELF 魔数后，不再计算复杂的偏移量，直接把从 ELF 头到 .bin 末尾的所有数据全部切下来。
◦ 相信 IDA：这种带有大量尾部垃圾的 .so 扔进 IDA，IDA 会自动通过启发式引擎找到可执行代码段，丝毫不影响搜字符串和反编译 JNI 函数。

🚀 三、 保姆级使用指南
第一步：准备环境
确保手机已 Root，App 正在前台运行。获取目标应用的 PID。
打开电脑终端，执行以下命令（将包名替换为你的目标 App）：
bash

adb shell pm list packages -3
adb shell pidof com.xxxx


第二步：启动脚本
在电脑终端运行该脚本：
bash

python UltimateTool.py

第三步：选择模式
脚本启动后，会弹出功能菜单。建议直接输入 4（一键执行全部流程）。
接着根据提示，输入你刚才获取到的 PID。
第四步：等待提取
屏幕上会滚动显示提取进度：
• 提示“找到 XX 个大于 2MB 的有效内存段”。
• 显示提取 DEX 和 SO 的进度与大小。
• 全程耗时大约 1-3 分钟。
第五步：分析结果
• 看 DEX：打开 Jadx，把 extracted_dex/ 里的文件全选拖进去。搜 Interceptor、sign、native，寻找网络层和加密入口。
• 看 SO：打开 IDA，把 extracted_so/ 里的文件拖进去。
⚠️ 注意：加载时如果提示 Segment loading problem，一定要选 Yes。
按 Shift+F12 搜 secp256k1、BIP39、AES 等密码学特征，找到底层加密算法的实现。
￼
⚠️ 四、 实战注意事项
1. 手机存储空间：内存 dump 偶尔会切出几个几百兆的巨型文件，建议手机至少保留 5GB 空闲空间。
2. App 闪退：如果 App 在提取过程中闪退，说明进程被杀掉了。重新打开 App 获取新 PID，重新跑一遍脚本即可。
3. 如何处理超大的 SO：如果你发现提取出来的 SO 有好几十 MB（里面混入了大量 Java 堆数据），在 IDA 里发现某个函数特别大且乱码，按 U 键把不需要的段取消定义，就能恢复干净视角。
